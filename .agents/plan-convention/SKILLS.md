# 설계 및 승인 컨벤션 (Plan Convention)

이 문서는 모든 구현 작업에 앞서 수행되어야 하는 설계 단계의 규격과 절차를 정의합니다.

## 1. 설계 문서 위치

- **경로**: `.plan/{도메인}/{작업명}.md`
- **파일명**: 작업의 핵심 내용을 담은 `kebab-case`를 사용합니다. (예: `auth/login-logic.md`)

## 2. 설계 문서(Plan) 양식

모든 설계 문서는 아래의 구조를 포함해야 합니다.

```md
# 설계: {도메인}-{작업명}

- **관련 이슈**: #이슈번호
- **작업 브랜치**: {유형}/{도메인}/#이슈번호-{간단설명}

## 1. 개요 및 목적
- 이번 작업으로 해결하려는 문제나 달성하려는 목표를 기술합니다.

## 2. 상세 파일 변경 명세 (중요)
- **생성/수정될 파일 목록**: 어떤 폴더에 어떤 파일을 만들거나 수정할지 정확히 나열합니다.
    - 예: `src/actions/auth/login.ts` (신규 생성)
    - 예: `src/hooks/auth/use-login.ts` (수정)
- **폴더 구조**: 변경으로 인해 새로 생기는 디렉토리 경로를 명시합니다.

## 3. 기술적 설계
- **데이터 구조**: DB 스키마 변경 사항, 전역 상태(Zustand) 변경 등.
- **아키텍처**: 컴포넌트 구조, 서버 액션 및 훅의 흐름도.
- **API 명세**: 새로 추가되거나 변경되는 API/RPC 정의.

## 4. 예외 처리 및 보안
- 발생 가능한 에러 시나리오와 대응 방안.
- RLS 정책 및 권한 검증 계획.

## 5. 검증 전략
- 빌드/린트 체크 계획.
- 기능 확인을 위한 테스트 시나리오.
```

## 3. 절차 (Workflow)

1. **지시**: Gemini CLI가 작업의 목표를 제시합니다.
2. **작성**: Codex가 위 양식에 따라 `.plan/`에 파일을 생성합니다. (별도의 `checklist.md`는 생성하지 않으며, 실제 작업 진행은 `.logs/`를 통해 관리합니다.)
3. **검토**: Gemini CLI가 파일을 읽고 기술적 타당성을 검토하여 사용자에게 요약 보고합니다.
4. **승인**: 사용자가 파일을 확인 후 최종 승인하면 구현을 시작합니다.
