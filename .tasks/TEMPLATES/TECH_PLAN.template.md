## 4. 기술 설계

### 데이터 흐름
- 서버 컴포넌트, Server Action, Supabase, 클라이언트 훅, 렌더링 컴포넌트의 흐름을 순서대로 적습니다.
- DB에서 필터링 가능한 조건은 쿼리 단계에서 처리합니다.

### 상태 관리
- 로컬 상태, URL 상태, TanStack Query, Zustand 등 사용할 상태의 소유 위치와 갱신 트리거를 적습니다.
- 불필요한 전역 상태나 중복 display type을 만들지 않습니다.

### 타입 및 검증
- 사용할 타입 정의, Zod 스키마, Supabase select 결과 타입을 적습니다.
- `as unknown as` 같은 이중 단언이 필요해 보이면 구현 전 대안을 먼저 기록합니다.

### UI 구현
- `DESIGN.md`와 연결되는 컴포넌트 구조, 반응형 기준, 접근성 고려사항을 적습니다.
- Tailwind 토큰과 기존 `cn` 패턴을 우선 사용합니다.

## 6. 성능 및 장애 대응
- N+1 쿼리, 불필요한 클라이언트 필터링, 과도한 리렌더링 가능성을 점검합니다.
- 이미지, 목록, 검색, 실시간 구독 등 성능에 민감한 부분의 대응 방안을 적습니다.
- 예상 가능한 실패 시나리오와 사용자 피드백 방식을 적습니다.

## 7. 검증 전략
- `npm run types` - 실행 필요 여부와 이유.
- `npm run build` - 빌드 및 타입 검증.
- `npm run lint` - 린트 검증. 프로젝트 스크립트가 없으면 사유를 적습니다.
- 수동 확인 시나리오 - 사용자가 실제로 수행할 핵심 흐름을 적습니다.
